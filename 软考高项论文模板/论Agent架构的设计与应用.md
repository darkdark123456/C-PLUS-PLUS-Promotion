​								论Agent架构的设计与应用

## 摘要

在企业数智化不断发展的背景下，我司原有智能办公平台存在跨部门固化工作流适配性差、异常场景人工干预率高，内置智能助手多轮对话上下文丢失、个性化偏好无法跨会话继承等痛点，严重制约协作效率。 **-----介绍背景和所在痛点。**

2025年 3月公司启动基智能体Agent 架构的平台升级项目，我担任总架构师全面主导方案设计与落地。

项目采用 LangChain+LangGraph 构建任务编排框架，结合LLM、混合检索和分层记忆机制，实现复杂任务的动态规划与执行。**------项目的整体技术背景**

针对任务规划死循环、记忆状态丢失和知识检索不准确等问题，我通过状态机约束、检查点持久化和混合检索优化等措施，提高了系统的可靠性。**-----解决问题**

项目实施后，复杂任务执行成功率由62%提高至94%，人工干预率显著下降35%,用户重复配置率下降70%，为企业办公自动化提供了技术支撑。**------成效**





**背景**

随着企业业务规模不断扩大，原有办公平台逐渐暴露出信息分散、流程待办响应滞后和跨系统协同效率低等问题。员工在处理会议预约、业务审批和统计报告等任务时，需要频繁切换业务系统，手动完成信息查询与流程衔接，难以满支持跨部门高效协同与敏捷决策。

为解决上述问题，公司启动智能办公平台升级项目，引入 Agent 架构，实现自然语言交互、任务自动规划和跨系统业务处理。

作为项目技术负责人，我统筹信息部门20余人，全面主导求分析、总体架构设计、核心模块开发及系统测试等工作。本项目采用 Python 和 FastAPI 构建后端服务，使用 LangChain+LangGraph 实现任务编排，通过 Redis 管理临时状态，利用 PostgreSQL 保存业务数据与任务检查点，并结合 Milvus 实现向量检索。系统通过统一工具接口对接会议预约、审批流转和消息通知等业务模块，形成完整的任务执行闭环。





**解决措施**

针对复杂任务执行过程不确定、业务模块耦合度高的问题，我采用分层架构，将 Agent 划分为感知交互、决策规划、执行控制和记忆管理四个模块。感知交互模块负责解析用户指令；决策规划模块利用大语言模型识别目标并生成任务计划；执行控制模块通过标准化接口调用外部工具；记忆管理模块负责维护上下文、任务状态和历史经验。各模块通过统一的数据结构交互，降低了系统耦合度。

在任务规划方面，我采用 LangGraph 构建状态图，将任务划分为意图识别、计划生成、工具执行和结果验证等节点，并根据执行结果决定后续路径。对于审批等流程固定的业务，系统采用预定义WorkFlow；对于临时提出的复杂需求，则由模型生成子任务及其依赖关系。为避免模型输出直接触发不受控的业务操作，我使用 Pydantic 校验工具参数，并设置最大执行次数、调用超时和终止条件。当工具返回异常时，系统将错误信息反馈给规划节点，决定重试、重新规划或转交人工处理。

在记忆管理方面，我设计了短期记忆、工作记忆和长期记忆协同机制。短期记忆依托上下文窗口保存当前对话，当上下文满载或者超过token上限等极限情况，通过摘要压缩历史信息，以此保证agent的正常工作；

工作记忆使用 Redis 保存任务进度和中间结果；

长期记忆则通过 PostgreSQL 持久化保存结构化历史记录，并利用 Milvus 检索经过筛选的历史经验。

为统一不同存储模块的访问方式，我设计了 Memory Access Interface，封装记忆读写、更新和检索操作。

考虑到 Redis 缓存可能过期或因服务重启而丢失，我进一步将关键任务检查点持久化至 PostgreSQL，记录当前节点、已完成步骤及必要的执行结果。任务中断后，系统读取最近一次有效检查点恢复执行，避免重新运行全部流程。对于已经产生外部业务副作用的操作，则通过幂等键和执行记录防止重复提交，必要时执行补偿操作或请求人工确认。



目实施过程中，我带领团队重点解决了任务规划死循环、跨会话状态丢失和知识检索准确率不足三个问题。

首先，针对任务规划死循环的问题，测试初期发现，Agent 在会议室预约场景中遇到时间冲突后，仍会重复选择原会议室，导致查询和规划节点反复执行。我通过 SkyWalking 链路追踪分析模型调用、工具执行和状态转换，发现规划模块既缺少明确的收敛条件，也未将失败结果纳入后续规划约束。



为此，我在 LangGraph 中增加最大迭代次数限制，并设置 `plan_status` 和 `rollback_flag` 状态字段，记录任务阶段及回溯标记。同时，将冲突会议室加入排除列表，使后续规划能够利用失败信息重新选择候选对象。

对于外部环境变化导致原计划失效的情况，系统根据检查点恢复到有效状态，再重新生成执行计划；超过重试上限后则终止自动执行。通过回归测试验证不同冲突场景，复杂任务执行成功率由62%提高至94%，重复调用现象明显减少。

其次，针对跨会话状态丢失的问题，我在联调过程中发现，部分跨月审批任务执行时间较长，Redis 中的中间状态提前过期后，Agent 无法识别已完成步骤，因而重复规划甚至再次提交请求。排查发现，固定 TTL 无法适应不同任务的持续时间，且关键状态缺少持久化保障。

针对这一问题，我根据任务状态动态调整缓存有效期，并将关键检查点写入 PostgreSQL。对于业务写操作，使用幂等键识别重复请求；对于并发更新，通过分布式锁控制同一任务的状态写入，避免执行结果相互覆盖。同时，利用任务标识关联日志，便于定位异常发生的具体环节。经过优化，测试任务的状态恢复能力得到改善，人工干预率较优化前降低约82%。

最后，针对知识检索结果相关性不足的问题，我采用向量检索与关键词检索相结合的混合检索方案。系统利用 Milvus 召回语义相近的文档，同时通过关键词匹配定位制度条款和业务编号，再融合排序结果，为大语言模型提供相关上下文。文档入库时保留版本、更新时间和权限信息，检索阶段执行权限过滤；当检索结果缺乏充分依据时，系统不直接生成确定性结论，而是提示用户补充信息。

在测试阶段，我使用人工标注的业务问题集评估检索效果，并根据错误案例调整文本分块和排序策略。测试结果显示，知识问答匹配准确率达到92%。此外，我组织团队开展功能测试、异常恢复测试和并发测试，以任务成功率、人工干预率和执行耗时作为主要评价指标，持续优化系统的可靠性与处理效率。



通过该项目的设计与实施，我认识到，Agent 架构的核心并非简单地调用大语言模型，而是通过任务规划、记忆管理、工具调用和状态控制，将模型推理能力转化为可执行、可验证和可追踪的业务流程。在实际开发中，必须设置明确的执行边界，建立可靠的状态持久化机制，并通过权限校验、幂等控制和异常恢复降低自动执行风险。同时，应结合测试数据持续评估任务成功率、检索质量和执行效率。只有将模型能力与工程化治理相结合，才能推动 Agent 从概念验证走向稳定的生产应用。
